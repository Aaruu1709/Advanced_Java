
-------------------------------------------------------
🔥 SOLID Principles
-------------------------------------------------------
1️⃣ S — Single Responsibility Principle (SRP)
🔥 Meaning:
A class should have ONLY ONE reason to change.

❌ BAD DESIGN (violates SRP)
class UserService {

    public void registerUser() {
        System.out.println("User registered");
    }

    public void sendEmail() {
        System.out.println("Email sent");
    }

    public void generateReport() {
        System.out.println("Report generated");
    }
}
🚨 Problem

This class handles:

user logic
email logic
reporting logic

👉 Too many responsibilities → fragile system

✅ GOOD DESIGN (SRP applied)
class UserService {
    public void registerUser() {
        System.out.println("User registered");
    }
}

class EmailService {
    public void sendEmail() {
        System.out.println("Email sent");
    }
}

class ReportService {
    public void generateReport() {
        System.out.println("Report generated");
    }
}
🧠 REAL INDUSTRY USE

In Spring Boot:

Controller → only request handling
Service → business logic
Repository → DB logic

👉 Each layer = single responsibility
----------------------------------------------------------
2️⃣ O — Open/Closed Principle (OCP)
🔥 Meaning:

Open for extension, but closed for modification
You should be able to add new features to your code without changing existing working code.

Break it down
Open for extension → You can add new behavior (new features)
Closed for modification → You should not change existing code that already works
👉 Meaning:
Your Java code should be written in a way that you can add new features without changing old working code.
❌ Bad Example (not OCP)

class NotificationService {
    void sendNotification(String type, String message) {
        if (type.equals("email")) {
            System.out.println("Sending EMAIL: " + message);
        } else if (type.equals("sms")) {
            System.out.println("Sending SMS: " + message);
        }
    }
}

🔥 Problem:
If you add WhatsApp → you must modify this class
Class keeps growing with if-else
Breaks Open/Closed Principle ❌

❌ 2. BAD “FIX” (Still not OCP)

Many beginners try this:

class NotificationService {

    void sendEmail(String message) {
        System.out.println("EMAIL: " + message);
    }

    void sendSMS(String message) {
        System.out.println("SMS: " + message);
    }

    void sendWhatsApp(String message) {
        System.out.println("WHATSAPP: " + message);
    }
}
🔥 Why this is still bad:
Still one big class
Every new feature → modify this class again
No abstraction
Still violates OCP ❌

✅ 3. PROPER OCP SOLUTION (BEST DESIGN)
Step 1: Create interface
interface Notification {
    void send(String message);
}

Step 2: Create separate classes
class EmailNotification implements Notification {
    public void send(String message) {
        System.out.println("EMAIL: " + message);
    }
}

class SMSNotification implements Notification {
    public void send(String message) {
        System.out.println("SMS: " + message);
    }
}

Step 3: Add new feature WITHOUT changing old code
class WhatsAppNotification implements Notification {
    public void send(String message) {
        System.out.println("WHATSAPP: " + message);
    }
}

Step 4: Use it
class NotificationService {
    void notifyUser(Notification notification, String message) {
        notification.send(message);
    }
}

🚀 Usage:
public class Main {
    public static void main(String[] args) {

        Notification email = new EmailNotification();
        Notification sms = new SMSNotification();
        Notification whatsapp = new WhatsAppNotification();

        NotificationService service = new NotificationService();

        service.notifyUser(email, "Hello Email");
        service.notifyUser(sms, "Hello SMS");
        service.notifyUser(whatsapp, "Hello WhatsApp");
    }
}


🎯 Final Understanding
❌ Bad approach:
Modify same class again and again
❌ Bad fix:
Still one class growing bigger
✅ Best approach:
Use interface + new classes
Add new features WITHOUT touching old code

👉 “Add new class, don’t edit old code.”

This class depends on Notification interface, not concrete classes.
That is clean design + OCP + polymorphism.
